## 1. Ringkasan eksekutif

**Pertanyaan operator:** (1) Apakah CLI resmi dengan mock IP VPS ke domain
server ter-publish bisa direalisasikan? (2) Apakah CLI resmi dilayani secara
otomatis oleh VPS + worker CF?

**Jawaban:** (1) **YA — tereproduksi 9/9 run EXIT=0 hari ini** (server 66281
tuxsnet + 74964 somedigit, mockhosts namespace, discovery asli, non-publishing).
(2) **YA sebagai relay** — payload pengukuran ber-origin di Worker edge
(`bytesFromWorkerDl` ≈ 100% byte client di lane worker-http/worker-ws;
0 byte worker di kontrol lokal) — **namun throughput per sesi tetap dibatasi
link VPS** (egress terukur ≈ 429–473 Mbps; semua lane dalam ±8% satu sama lain).
Kombinasi "hasil akhir > bandwidth VPS" untuk CLI resmi **tidak dapat dicapai
lewat arsitektur relay ini** (fisika: semua byte transit NIC VPS) dan jalur
edge langsung untuk CLI resmi tetap mustahil di CF free (protokol biner
NetGauge vs inbound HTTP-only Workers — lihat `speedtest-cli_analysis/KESIMPULAN-FINAL.md`
§1.2). Ini konsisten dengan verdict audit 26–27 Nov; sesi ini menambah
bukti segar + remediasi.

## 4. Analisis pertanyaan inti (bandwidth > VPS dengan CLI resmi)

Fakta fisika + platform (semua telah diverifikasi empiris oleh sesi-sesi
sebelumnya + sesi ini):

1. CLI resmi hanya berbicara **NetGauge biner** (TCP/TLS + UDP loss) ke
   host:port dari server-list Ookla. CF Workers free hanya menerima
   inbound HTTP/HTTPS/WebSocket → **tidak ada jalur edge langsung**
   (BLOCKED_BY_PROTOCOL; Spectrum Enterprise pun hanya proxy ke origin VPS
   — tetap transit link VPS).
2. Bridge relay membuat worker menjadi **origin** payload, tetapi setiap
   byte tetap melewati NIC VPS → **per-sesi = egress VPS** (terbukti: semua
   lane ≈ 430–473 Mbps; ingress 872 Mbps tak terpakai untuk DL).
3. Server-list Ookla tertutup (hanya host terdaftar); `-s` memilih dari
   daftar itu. Mock `/etc/hosts` hanya berlaku di mesin uji (lab), bukan
   produksi publik.

**Kesimpulan:** dengan 1 VPS + CF free, hasil speedtest CLI resmi **tidak
mungkin melebihi bandwidth VPS**. Opsi yang tersisa (jujur dan valid):

| Opsi | Efek | Catatan |
|---|---|---|
| Relay worker (saat ini) | origin payload di edge, hemat generasi VPS; kapasitas per sesi tetap = link VPS | Sudah produksi + terbukti |
| Daftar resmi Ookla (Hosting Program / A12) | CLI resmi tanpa mock menargetkan VPS | Keputusan komersial Ookla; kapasitas tetap link VPS |
| Worker pool + lane web/custom (front 302) | agregasi NYATA VPS+edge > link VPS | Hanya untuk klien HTTP custom (sudah ada, `HYBRID_VPS_DL_SHARE`) |
| Multi-VPS / ECMP / link lebih besar | kapasitas naik sesungguhnya | Di luar cakupan CF free |

## 5. Rekomendasi tindak lanjut

1. **Angkat limit per-IP bridge** (F-11) sebelum dipakai multi-pelanggan:
   mis. `SPEEDTEST_BRIDGE_CONN_RATE_PER_MIN=2000`,
   `SPEEDTEST_BRIDGE_MAX_CONN_PER_IP=5000` (+ restart bridge).
2. Sertakan `config/99-speedtest-tuning.conf` ke alur installer (saat ini
   diterapkan manual di VPS via sysctl.d).
3. Rencanakan perpanjangan cert wildcard via **DNS-01** sebelum 8 Jan 2027
   (konflik redirect nPerf :80 — F-03).
4. Investigasi F-09 (loss UDP lane worker-http) bila angka loss mau
   ditampilkan ke pengguna akhir.
5. Pertahankan kanal cadangan `gw.lumajangnetworks.my.id` (F-02) +
   dokumentasikan di runbook; UA otomasi wajib custom (F-13).
